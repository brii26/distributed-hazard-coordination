\section{Menjalankan di Kubernetes}

\subsection{Membuat Cluster}

Prasyarat: VirtualBox, \texttt{kubectl}, \texttt{ssh}, \texttt{curl}, \texttt{mkfs.vfat} dan \texttt{mcopy}, sekitar 30 GB disk kosong, dan sekitar 7 GiB RAM kosong untuk tiga VM bawaan (\texttt{doc/TOPOLOGY.md}). Tiga VM dibuat dan k3s dipasang dengan dua skrip, lalu \texttt{kubectl} diarahkan ke cluster:

\begin{codebox}
deploy/cluster/up.sh
deploy/cluster/k3s.sh
export KUBECONFIG=$HOME/vms/k3s/kubeconfig
kubectl get nodes
\end{codebox}

Kedua skrip aman dijalankan ulang. Cluster dihapus dengan \texttt{deploy/cluster/down.sh destroy}. Skrip \texttt{k3s.sh} juga menyalakan \textit{registry} \textit{image} di node-a (\texttt{10.77.0.11:5000}).

\subsection{Membangun Image dan Deploy}

Tiap \textit{service} Go dibangun dari foldernya di \texttt{services/} dan di-\textit{push} ke \textit{registry} dari host, misalnya untuk \textit{Aggregator}:

\begin{codebox}
docker build -t 127.0.0.1:5000/aggregator:0.1.0 services/aggregator
docker push 127.0.0.1:5000/aggregator:0.1.0
\end{codebox}

Nama dan tag \textit{image} ditetapkan pada blok \texttt{images} di \texttt{deploy/kustomization.yaml}. Setelah semua \textit{image} ada, seluruh sistem di-\textit{deploy} dengan satu perintah:

\begin{codebox}
cp .env.example .env
deploy/deploy.sh
\end{codebox}

Nilai \texttt{change-me} di \texttt{.env} diganti dulu. \texttt{deploy.sh} membuat \textit{namespace}, Secret dari \texttt{.env}, ConfigMap skema dan \textit{broker}, menerapkan manifest dengan Kustomize, menunggu tiap \textit{rollout}, lalu menjalankan pemeriksaan label dan sumber daya (\texttt{deploy/check.sh}). Skrip berhenti dengan galat dan daftar pod yang belum Running bila ada yang tidak siap dalam waktu \texttt{TIMEOUT} (bawaan 300 detik per workload). Kesebelas \textit{image} dapat dibangun sekaligus dengan satu \textit{loop}:

\begin{codebox}
for s in aggregator bmkg-mock pvmbg-mock auth-service client-facing-api web-frontend dashboard-updater notifier audit-logger field-report-processor situation-summarizer; do
  docker build -t 127.0.0.1:5000/$s:0.1.0 services/$s
  docker push 127.0.0.1:5000/$s:0.1.0
done
\end{codebox}

\subsection{Membuka Antarmuka}

Web Frontend dibuka pada NodePort 30080 dan Client-Facing API pada NodePort 30081 di alamat node, misalnya \texttt{http://10.77.0.11:30080} (\texttt{deploy/web-frontend.yaml}, \texttt{deploy/client-facing-api.yaml}). Antarmuka lain tidak dibuka dan dijangkau lewat \texttt{kubectl port-forward}, misalnya \texttt{kubectl -n sistem-informasi-kebencanaan-bnpb port-forward svc/grafana 3000} untuk Grafana (kata sandi pengguna \texttt{admin} dibuat sekali oleh \texttt{make-secrets.sh}, \texttt{docs/OBSERVABILITY.md}). Kedua NodePort diperiksa pada klaster tiga VM tanggal 23 November 2026 dengan \texttt{kubectl get svc}: \texttt{web-frontend} 30080 dan \texttt{client-facing-api} 30081.

Skrip skenario ada di \texttt{tests/scenarios/}: \texttt{problem1.sh} sampai \texttt{problem5.sh} dan \texttt{all.sh} dari Milestone 1, ditambah \texttt{rolling-update.sh}, \texttt{autoscale.sh}, \texttt{audit-checksum.sh}, \texttt{critical-alerts.sh}, \texttt{trace-check.sh}, dan \texttt{gameday.sh}. Batasan yang perlu diketahui pembaca:
\begin{itemize}
\item Tidak ada \textit{run} orkestrator tunggal. Hasil di tabel berasal dari \textit{run} terpisah pada \textit{cluster} yang sama, sebagian pada \textit{image} yang diganti di antaranya.

\end{itemize}

\section{Pengembangan Lokal dengan Docker Compose}

Bagian ini sampai akhir bab berasal dari Milestone 1 dan berlaku untuk pengembangan di satu mesin dengan \texttt{docker-compose.yml}. Demo Milestone 2 berjalan di Kubernetes, dan Compose tidak menjalankan fitur replika, shard, maupun \textit{lease}. Langkahnya sama dengan bagian \textit{Quick start} di README.


Prasyarat yang dibutuhkan adalah Go 1.26 atau lebih baru, Docker beserta Docker Compose, \texttt{git}, serta \texttt{curl} dan \texttt{jq} untuk perintah skenario. Dari \textit{clone} baru, sistem dijalankan dengan perintah berikut:

\begin{codebox}
git clone https://github.com/brii26/distributed-hazard-coordination.git
cd distributed-hazard-coordination
cp .env.example .env
docker compose up -d --build --wait
docker compose ps
\end{codebox}

Nilai contoh pada \texttt{.env} sudah cukup untuk menjalankan sistem secara lokal. Perintah \texttt{docker compose up} membangun seluruh \textit{image} dan baru selesai setelah semua \textit{health check} lolos, sehingga ketika perintah itu kembali sistem sudah siap. \textit{Build} pertama memerlukan beberapa menit. Pada \texttt{docker compose ps}, semua \textit{service} harus berstatus \textit{running}, dan yang memiliki \textit{health check} berstatus \textit{healthy}. Sistem dihentikan dengan \texttt{docker compose down}, dan opsi \texttt{-v} menghapus basis data, token PVMBG, dan berkas deduplikasi \textit{consumer} untuk memulai dari nol.

\subsection{Membuka Jaeger}

Jaeger menampilkan jejak permintaan lintas \textit{service}. Buka \texttt{http://localhost:16686}, pilih \textit{service} pada kolom \textit{Service}, misalnya Client-Facing API, lalu tekan \textit{Find Traces}. Satu jejak menunjukkan rangkaian panggilan dari Client-Facing API ke \textit{Aggregator}. ID jejak sama dengan \texttt{correlation\_id} pada log, sehingga sebuah permintaan dapat dilacak dari log ke jejaknya. Tab \textit{Monitor} menampilkan laju permintaan, galat, dan latensi per \textit{service}. Jejak hanya muncul bila \texttt{TRACING\_ENABLED} bernilai \texttt{true}, yang merupakan nilai bawaan. Jejak dan metrik berada di memori sehingga hilang saat Jaeger dijalankan ulang, dan Jaeger yang mati tidak memengaruhi \textit{service} lain.

\section{Skenario Milestone 1 di Compose}

Setiap problem punya satu skrip di \texttt{tests/scenarios/} yang dijalankan terhadap sistem yang sudah berjalan. Skrip membaca \texttt{.env}, menjalankan langkah pemicu, mencetak perintah dan keluarannya apa adanya, lalu menilai tiap pemeriksaan dengan baris \texttt{PASS} atau \texttt{FAIL}. Baris terakhir adalah \texttt{RESULT: PASS} atau \texttt{RESULT: FAIL}, dan kode keluar skrip tidak nol bila ada yang gagal. Keluaran yang sama dipakai sebagai bukti pada subbab Bukti Penyelesaian di Bab VI sampai X.

\begin{codebox}
tests/scenarios/problem1.sh
tests/scenarios/problem2.sh
tests/scenarios/problem3.sh
tests/scenarios/problem4.sh
tests/scenarios/problem5.sh
tests/scenarios/all.sh
\end{codebox}

Perintah \texttt{all.sh} menjalankan kelimanya berurutan dan menutup dengan satu baris hasil per problem. Skrip berhenti dengan kode 2 dan pesan yang jelas bila \texttt{.env} belum ada atau sistem belum berjalan.

Mengubah latensi PVMBG membuat ulang \textit{container}-nya, dan skrip memulihkannya setelah selesai.

\subsection{Mengambil Bukti Milestone 1}

Untuk bukti pada Bab VI sampai X, tangkap layar terminal pada bagian berikut, atau simpan keluarannya dengan \texttt{tests/scenarios/problemN.sh | tee bukti-problemN.txt}.

\begin{itemize}
\item Problem 1: kedua daftar \texttt{confidence}, sebelum dan sesudah sakelar, serta tabel \texttt{hazard\_events} dengan kolom \texttt{has\_confidence}.
\item Problem 2: lima waktu respons gempa, kedua keluaran \texttt{.meta} saat \textit{outage}, dan keluaran \texttt{.meta} setelah pulih. Hasil uji beban ada pada \texttt{tests/load/results/}. Grafik jejak dapat diambil dari Jaeger.
\item Problem 3: tiga kode status kredensial tertukar, daftar \textit{key} untuk Media, dan tiga baris \texttt{HTTP}, \texttt{jwt}, dan \texttt{refresh\_token} saat penyegaran.
\item Problem 4: keluaran \texttt{docker compose ps} saat Notifier berhenti dan daftar keterjangkauan basis data.
\item Problem 5: kedua keluaran \texttt{list\_queues} serta jumlah baris log audit sebelum dan sesudah. Antrean juga terlihat di antarmuka RabbitMQ.
\end{itemize}
